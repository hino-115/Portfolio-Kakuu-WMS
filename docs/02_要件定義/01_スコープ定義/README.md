# スコープ定義の検討・判断記録

本資料では、KAKUU WMSのスコープ定義において検討した事項と、その判断理由を記録する。

## 1. スコープ定義の基本方針

### 1.1 実装範囲の明確化

実装したい機能を広げすぎると、ポートフォリオとして完成させにくくなるため、「今回実装」「将来拡張」「対象外」を明確に分けた。

棚卸、佐川急便API連携、ハンディターミナルによるピッキングなどは将来拡張とし、今回の開発範囲を現実的な規模に整理した。

### 1.2 業務スコープと機能スコープの分離

業務スコープと機能スコープが混同しやすかったため、以下を別々に整理した。

- **業務スコープ**：業務としてどこまで扱うか
- **機能スコープ**：システムとして何を実装するか

これにより、手作業として残す工程とシステム化する工程を明確にした。

## 2. 業務別の検討事項

### 2.1 ピッキング業務

ピッキング業務をどこまで対象にするか検討した結果、以下のように整理した。

- **今回実装**：ピッキングリストの作成・印刷
- **システム対象外**：実際の商品取り出し（手作業で実施）
- **将来拡張**：ハンディターミナルを使用したピッキング

これにより、今回の実装と将来的なハンディターミナル導入との境界を明確にした。

### 2.2 出庫・配送・出荷の境界

出庫・配送・出荷の境界が曖昧だったため、以下のように整理した。

- **システム対象**：出荷情報の確定まで
- **システム対象外**：実際の商品搬出および佐川急便による配送

物流業務全体を無理にシステム化しない構成とした。

### 2.3 オリコン単位の在庫移動

在庫管理の範囲を検討する中で、オリコン単位の在庫移動まで実装すると機能が複雑になるため、今回は対象外とした。

一方、将来的にはオリコンを丸ごと移動する方式で拡張できるよう、運用ルールを残している。

### 2.4 在庫不足時の出荷処理

出荷時の在庫不足を当初のスコープで十分に考慮できていなかったため、以下の機能を追加した。

- 部分引当
- 一部出荷
- 未出荷数量の保持
- 在庫補充後の再引当

これにより、注文を作り直すことなく、同じ注文から複数回出荷できる構成へ改善した。

## 3. 利用者・外部連携・非業務機能

### 3.1 業務ロールとアクセス権限

利用者ごとの業務とシステム権限を混同しないよう整理した。

仕入れ担当、入荷担当、在庫管理担当、出荷担当などの業務ロールは定義したが、担当者別の詳細なアクセス制御は今回実装せず、将来拡張とした。

### 3.2 外部システムとの連携範囲

外部システムとの連携範囲が広がりやすかったため、以下のように整理した。

- **今回実装**：仕入先・卸先とのCSV受け渡しをメールと手動取込で行う
- **将来拡張**：ファイル共有、自動取込

今回の実装範囲と将来構想を明確に分離した。

### 3.3 認証・バックアップ・権限管理

認証・バックアップ・権限管理などの非業務機能をすべて実装すると規模が大きくなるため、今回の対象を限定した。

- **今回実装**：社員マスタを利用した最低限のログイン認証
- **将来対応**：実運用向けの高度なセキュリティ、バックアップ、詳細な権限管理

## 4. 後工程との整合性確認

スコープ整理後も、業務フローやユースケースとの間に不足がないか見直した。

その結果、在庫引当や未出荷分の再引当など、後から判明した機能を各スコープへ反映した。

資料を一度作って終わりにせず、後工程で見つかった不足を前工程へ戻して修正することで、資料間の整合性を高めた。
