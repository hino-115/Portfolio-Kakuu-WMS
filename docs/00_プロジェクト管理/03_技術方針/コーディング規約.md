# コーディング規約

## 1. 基本方針

- 本規約は、KAKUU WMSにおけるコードの可読性・保守性・記述の統一を目的とする。
- コードの役割や処理内容が分かる記述を優先する。
- 本規約で定めていない事項は、必要に応じて設計・実装時に判断する。
- 文字コードはUTF-8、改行コードはLFとする（技術方針に従う）。

## 2. 命名規則

### 2.1 命名形式の種類

- ローワーキャメルケース（lowerCamelCase）
- アッパーキャメルケース（UpperCamelCase / PascalCase）
- ローワースネークケース（lower_snake_case）
- アッパースネークケース（UPPER_SNAKE_CASE / SCREAMING_SNAKE_CASE）
- ケバブケース（kebab-case）
- フラットケース（flatcase）
- トレインケース（Train-Case）
- COBOLケース（COBOL-CASE）
- パスケース（path/case）
- ドットケース（dot.case）
- ハンガリアン記法（Hungarian Notation）

各命名形式の詳細については、別資料に記載する。上記は命名形式の一覧であり、すべての形式を実装で採用するという意味ではない。

### 2.2 クラス名

- アッパーキャメルケース（PascalCase）を使用する。
- クラスの役割や内容が分かる名称とする。
- 単語を省略しすぎず、意味が読み取れる名称とする。
- Controller / Service / Repositoryなど、レイヤを示す接尾辞は省略しない。

例：`LoginController`、`InventoryService`、`ItemRepository`

### 2.3 メソッド名

- ローワーキャメルケース（lowerCamelCase）を使用する。
- 原則として「動詞 + 対象名称」の形式とする。
- メソッド名から処理内容を推測できる名称とする。
- 単語を省略しすぎず、意味が読み取れる名称とする。

主な動詞の使い分け：

| 動詞 | 用途 |
| --- | --- |
| `get` | 取得対象が特定されている値・データの取得 |
| `find` | 条件による単一データの検索 |
| `search` | 条件による複数データの検索 |
| `list` | 一覧の取得 |
| `create` | 新しいオブジェクト・データの作成 |
| `register` | 業務上の登録処理 |
| `update` | 既存データの更新 |
| `delete` | データの削除 |
| `check` | 条件・状態の確認 |
| `validate` | 入力値・業務条件の検証 |
| `calculate` | 計算 |
| `convert` | 変換 |
| `build` | オブジェクト・データの組み立て |
| `generate` | 生成 |

`save` は現時点では用途を定めない。必要になった場合に使用条件を規約へ追加する。

例：`getItemById`、`findItemByCode`、`searchItems`、`listWarehouses`、`registerInbound`、`updateInventory`

### 2.4 変数名

- ローワーキャメルケース（lowerCamelCase）を使用する。
- 原則として、変数の内容や用途が分かる名称とする。
- 短縮した変数名は、スコープが限定され、用途が明確な場合のみ使用を認める。

#### 短縮変数名の使用

- 1つのループ文内でのみ使用するループカウンタについては、`i`、`j`、`x` などの短い変数名を使用してよい。
- ループ文内だけで使用する一時変数については、用途が明確であれば短縮した変数名を使用してよい。
- メソッド全体で使用する変数については、短縮した変数名を使用しない。
- 変数のスコープが2つ以上のループ文や処理ブロックにまたがる場合は、`i`、`j` などを含む短縮変数名を使用しない。
- スコープが広くなるほど、変数の内容や用途が明確に分かる名称を使用する。

#### 真偽値・状態値

- 真偽のみを扱う場合は、原則として `boolean` 型を使用する。
- 真偽値を表す変数名には、状態や判定内容が分かるよう、用途に応じて以下の接頭辞を使用する。
  - `is`：対象が特定の状態であるか。例：`isActive`
  - `has`：対象が何らかの情報や状態を保持しているか。例：`hasStock`
  - `can`：対象の処理を実行可能か。例：`canShip`
  - `should`：対象の処理を実行すべきか。例：`shouldRetry`
- `flag` は使用しない。
- 複数の状態や分類を扱う場合は、用途に応じて以下の名称を使用する。

| 名称 | 用途 | 例 |
| --- | --- | --- |
| `status` | 現在の進行状況や業務状態 | `orderStatus` |
| `state` | システム内部の状態 | `processState` |
| `type` | 種類・分類 | `orderType` |
| `mode` | 動作モード | `operationMode` |
| `level` | 段階・重要度 | `priorityLevel` |
| `phase` | 工程段階 | `processPhase` |
| `category` | カテゴリ分類 | `itemCategory` |
| `kind` | `type` よりやや一般的な種類・分類 | — |

### 2.5 定数名

- 定数名はアッパースネークケース（UPPER_SNAKE_CASE）を使用する。
- `static final` で定義する定数は、名前から値の意味や用途が分かる名称とする。
- 数値や文字列を直接記述すると意味が分かりにくくなる場合は、原則として定数化する。
- マジックナンバーになり得る値は、可能な限り定数として定義する。
- 単位を持つ値については、必要に応じて名称に単位を含める。

例：`MAX_RETRY_COUNT`、`TIMEOUT_SECONDS`、`DEFAULT_WAREHOUSE_CODE`

### 2.6 パッケージ名

- パッケージ名はすべて小文字とする。
- 単語の区切りには `.` を使用する。
- 大文字、ハイフン、アンダースコアは原則として使用しない。
- パッケージ名から役割や責務が分かる名称とする。
- Controller / Service / Repositoryなど、レイヤを表す名称は省略しない。
- ルートパッケージ名は本規約では定めず、プロジェクト構成を決定する際に別途定義する。

### 2.7 ファイル名

- Javaファイル名は、対応するpublicクラス名と一致させ、PascalCaseを使用する。
- JSP・HTML・CSS・JavaScript・SQL・propertiesファイル名は、原則として小文字とする。
- 複数単語からなるファイル名には、原則としてケバブケース（kebab-case）を使用する。
- ファイル名から役割や内容が分かる名称とし、不明瞭な省略を避ける。
- フレームワークやツール側で名称が定められているファイルは、その既定名称を優先する。

例：`InventoryService.java`、`LoginController.java`、`order-list.jsp`、`inventory-search.js`、`common-layout.css`、`create-table.sql`、`initial-data.sql`、`application.properties`

## 3. コードの書式

### 3.1 インデント

- Javaのインデントはスペース4文字とする。
- インデントにタブ文字は使用しない。

### 3.2 波括弧

- 開始波括弧 `{` は、原則として宣言文や制御文と同じ行に記述する。
- 終了波括弧 `}` は、原則として独立した行に記述する。
- `if`、`else`、`for`、`while` などの制御文では、処理が1行の場合でも波括弧を省略しない。
- `else` および `catch` は、直前の終了波括弧と同じ行に記述する。

```java
if (isValid) {
    register();
} else {
    showError();
}
```

### 3.3 1行の文字数と改行

- Javaコードは、原則として1行120文字以内とする。
- 1行が長くなる場合は、処理の意味が分かる単位で改行する。
- メソッドの引数が複数行にまたがる場合は、原則として1引数につき1行に記述する。
- メソッドチェーンが長くなる場合は、メソッド呼び出し単位で改行する。
- 文字列リテラルや可読性を損なう場合などは、120文字を超えることを許容する。
- 文字数制限を守るためだけに、変数名やメソッド名を不明瞭に短縮しない。

### 3.4 空行・スペース

#### 空行

- メソッドとメソッドの間には、原則として空行を1行設ける。
- 処理のまとまりが変わる箇所には、必要に応じて空行を設ける。
- 不必要に連続した空行を使用しない。
- メソッドの開始直後および終了直前には、原則として空行を設けない。

#### スペース

- `if`、`for`、`while`、`switch`、`catch` などの制御文と、直後の `(` の間にはスペースを1文字設ける。
- 代入演算子、比較演算子、二項算術演算子の前後には、原則としてスペースを1文字設ける。
- カンマの後にはスペースを1文字設ける。
- メソッド名と直後の `(` の間にはスペースを設けない。
- 単項演算子およびインクリメント・デクリメント演算子と、その対象の間にはスペースを設けない。
- 行末に不要なスペースを残さない。

### 3.5 クラス内の記述順序

クラス内の要素は、原則として以下の順序で記述する。

1. 定数（`static final`）
2. staticフィールド
3. インスタンスフィールド
4. コンストラクタ
5. publicメソッド
6. protectedメソッド
7. privateメソッド

- メソッドは、原則としてアクセス修飾子ごとにまとめる。
- publicメソッドを先に配置し、クラスが提供する機能を把握しやすくする。
- 同じアクセス修飾子のメソッドは、関連する処理を近くに配置する。
- 各要素のまとまりの間には、必要に応じて空行を設ける。

### 3.6 import文

- import文は、原則として使用するクラスを個別に記述する。
- ワイルドカードimport（`*`）は、原則として使用しない。
- Eclipseの自動import整理などによってワイルドカードimportが生成された場合は、使用を許容する。
- ワイルドカードimportによってクラス名の競合や可読性の低下が生じる場合は、個別importに変更する。
- 使用していないimport文は削除する。

#### import文の記述順序

- Java標準ライブラリと外部ライブラリのimport文は、同一グループにまとめる。
- プロジェクト内のクラスのimport文は、空行を1行挟んで別グループにまとめる。
- 各グループ内のimport文は、原則としてアルファベット順に記述する。
- import文のグループ間には、空行を1行設ける。

Eclipseのimport順序に関する設定は、技術設定側で管理する。

### 3.7 アノテーション

- アノテーションは、原則として対象となるクラス・フィールド・メソッドなどの宣言の直前に記述する。
- 複数のアノテーションを付与する場合は、原則として1行に1つずつ記述する。
- アノテーションの並び順は、役割や可読性を考慮して決定する。
- アノテーションの順序が動作に影響する場合は、必要な順序を優先する。

### 3.8 アクセス修飾子

- クラス・フィールド・メソッドのアクセス範囲は、必要最小限とする。
- 外部から利用する必要がある場合のみ、`public` を使用する。
- クラス内部でのみ使用するフィールドやメソッドは、原則として `private` とする。
- `protected` は、継承先からの利用が必要な場合に使用する。
- アクセス修飾子を省略する場合は、同一パッケージ内での利用を意図していることを明確にする。
- 将来的な利用の可能性だけを理由に、アクセス範囲を広げない。

## 4. メソッド・クラスの設計

### 4.1 メソッドの責務

- メソッドは、原則として明確な目的や責務を持つものとする。
- 1つの目的を実現するために、複数の処理を組み合わせることは許容する。
- 関連性の低い処理や独立した目的を持つ処理が混在する場合は、メソッドの分割を検討する。
- メソッドの責務や処理内容が、名称から推測できる構成とする。

### 4.2 メソッドの長さと分割基準

- メソッドの行数に一律の上限は設けない。
- メソッドは、処理の目的や流れが理解しやすい構成とする。
- 複数箇所で共通化できる処理は、必要に応じて別メソッドへの分割を検討する。
- 可読性や保守性の向上が期待できる場合は、メソッドの分割を行ってよい。
- 単に行数が多いことだけを理由に、分割を強制しない。
- 過度な細分化によって処理の流れが分かりにくくならないようにする。

### 4.3 メソッドの引数と戻り値

- メソッドの引数の数に、一律の上限は設けない。
- 引数が少数の場合は、必要に応じて個別に指定する。
- 関連する複数のデータを受け渡す場合は、DTOなどのオブジェクトの利用を検討する。
- DTOは、データの受け渡しを目的として使用する。
- JavaBeanとDTOを独自の分類で厳密に区別することはしない。
- 戻り値は、処理結果や呼び出し元で必要な情報に応じて適切な型を選択する。
- 引数の数を減らすことだけを目的として、関連性のないデータを1つのオブジェクトにまとめない。
- 具体的なデータ保持クラスの構成は、データ設計・内部設計で決定する。

### 4.4 Optionalの使用

- 単一データの検索において、結果が存在しない可能性がある場合は、原則として `Optional<T>` を戻り値に使用する。
- 複数件の検索結果には、原則として `List<T>` を使用し、該当データがない場合は空のリストを返す。
- 必ず値が存在する処理では、通常の戻り値の型を使用する。
- DTOなどのフィールドには、原則として `Optional` を使用しない。
- `Optional.get()` の無条件な呼び出しは避け、`orElseThrow()` などを適切に使用する。
- 検索結果が存在しないことを業務上のエラーとして扱う場合は、必要に応じてService側で業務例外へ変換する。

### 4.5 クラスの責務と分割基準

- クラスは、役割や目的が明確な構成とする。
- クラスの分割は、原則として必要最小限にとどめる。
- 明らかに異なる責務を持つ処理が混在する場合は、クラスの分離を検討する。
- 複数のクラスで利用する共通処理が発生する場合は、必要に応じて共通クラスへの分割を行う。
- 共通化する際は、コードの類似性だけでなく、処理の目的や業務上の意味も考慮する。
- 将来的に共通化することが具体的に想定される処理については、事前の分割を許容する。
- 将来的な利用の可能性だけを理由に、不必要なクラス分割を行わない。
- クラスの行数による一律の分割基準は設けない。
- 必要以上のクラス分割によって、処理の流れや構成が複雑にならないようにする。

### 4.6 重複コードと共通化

- 同一または類似する処理が複数箇所に存在する場合は、共通化を検討する。
- 同じ処理が2箇所以上に存在することだけを理由に、共通化を強制しない。
- 共通化する際は、コードの類似性だけでなく、処理の目的や業務上の意味を考慮する。
- 業務上の意味や変更理由が異なる処理は、無理に共通化しない。
- 共通化によって、クラス間の依存関係が不必要に複雑にならないようにする。
- 共通処理の修正が、利用している他のクラスに意図しない影響を与えないよう、影響範囲を確認する。
- 共通処理を変更した場合は、必要に応じて利用元の処理もテストする。
- 共通化によって不具合の発生リスクや保守負担が増える場合は、処理を分離したまま維持することを許容する。

### 4.7 nullの取り扱いとNullPointerExceptionの防止

- `null` が発生する可能性のある箇所を把握し、適切に処理する。
- 利用者からの入力値は、原則としてBean Validationなどを使用して検証する。
- プログラム内部で `null` を許容しない値を受け取った場合は、`Objects.requireNonNull()` などを使用し、早期に例外を発生させる。
- 単一データの検索結果が存在しない可能性がある場合は、原則として `Optional<T>` を使用する。
- 複数件の検索結果は、原則として `null` ではなく空のコレクションを返す。
- `null` チェックは必要な箇所で実施し、不必要なチェックを繰り返さない。
- `null` を検出した場合の処理は、業務仕様やメソッドの責務に応じて決定する。
- `NullPointerException` を通常の業務分岐として利用しない。
- `Optional.get()` を無条件に呼び出さない。

## 5. コメント・Javadoc

- クラスおよびメソッドには、原則としてJavadocを記載する。
- Javadocには、クラスやメソッドの役割・仕様が分かる内容を記載する。
- 処理内部の意図、理由、注意点については通常コメントを使用する。
- コードを読めば分かる内容を、そのままコメントで繰り返さない。
- コメントアウトした古いコードは残さず、変更履歴はGitで管理する。

### 5.1 コメント形式

- `//`：処理内の意図・理由・注意事項などの通常コメント。
- `/* ... */`：必要に応じて使用する複数行の通常コメント。
- `/** ... */`：クラス・メソッドのJavadoc。

### 5.2 Javadocの例外

以下の場合は、Javadocの記載を省略してよい。

- `@Override` するメソッドで、親クラスまたはインターフェース側のJavadocで仕様が十分に説明されている場合。
- getter・setterなど、処理内容が明白で追加説明の必要がない単純なメソッド。
- フレームワークによって定型的に実装され、役割が明確なメソッド。

ただし、オーバーライド後に独自の処理や注意事項が追加されている場合は、必要な内容をJavadocまたは通常コメントで補足する。

## 6. 例外処理

### 6.1 基本方針

- 例外は原則として握りつぶさない。
- 例外を捕捉する場合は、可能な限り具体的な例外型を使用する。
- `Exception` を直接捕捉する処理は、必要性がある場合に限定する。
- 業務上想定されるエラーと、システム上の予期しないエラーを分けて扱う。
- システムエラーについては、必要な情報をログへ出力する。
- 例外メッセージやスタックトレースを、そのまま利用者画面へ表示しない。
- 必要に応じて独自例外を定義し、処理の意味が分かる形で例外を扱う。

### 6.2 業務例外

業務ルール上、処理を継続できない場合に発生する例外とする。

例：

- 在庫数が不足している。
- 対象データが業務上許可されていない状態である。
- 指定された対象が存在しない。
- 入力内容は形式上正しいが、業務条件を満たしていない。

業務例外については、利用者が原因を理解できる内容として扱う。

### 6.3 システム例外

システムの実行環境やプログラム上の問題など、通常の業務処理では想定しない異常によって発生する例外とする。

例：

- データベースへの接続失敗。
- SQL実行時の予期しないエラー。
- プログラム内部の予期しない例外。
- 外部リソースへの接続失敗。

システム例外については、詳細をログに記録し、利用者には内部情報をそのまま表示しない。

### 6.4 例外の捕捉と伝播

- 例外は、その階層で適切に対処できる場合に捕捉する。
- その階層で対処できない例外は、原則として上位へ伝播させる。
- 必要に応じて例外を再スローする場合は、原因となった例外の情報を保持する。
- 最終的に共通例外処理などで捕捉し、例外の種類に応じたログ出力や利用者向けのエラー表示を行う。
- 各階層で不要な `try-catch` を繰り返さない。

通常の入力バリデーションエラーは、原則として入力画面側で扱う。

## 7. ログ出力

### 7.1 基本方針

- ログ出力には、SLF4JおよびLogbackを使用する。
- ログレベルは、処理の重要度や異常の内容に応じて使い分ける。
- 同一の例外について、複数の階層で重複してログ出力しない。
- パスワードなどの機密情報はログに出力しない。
- `System.out.println()` や `printStackTrace()` をログ出力の代わりに使用しない。

### 7.2 ログレベルの使い分け

| レベル | 用途 |
| --- | --- |
| `ERROR` | 予期しないシステム例外など、処理を正常に完了できない異常 |
| `WARN` | 処理の継続可否にかかわらず、注意や調査が必要な状態 |
| `INFO` | 通常の業務処理の記録、および想定内の業務例外 |
| `DEBUG` | 開発・調査時に必要な処理内容や条件の確認 |
| `TRACE` | 詳細な処理経過の追跡 |

### 7.3 業務例外のログ出力

- 想定内の業務例外は、原則として `INFO` で記録する。
- 注意や調査が必要な業務例外は、`WARN` で記録する。
- 通常の入力バリデーションエラーは、原則としてログ出力しない。
- 業務例外であることのみを理由に `ERROR` として記録しない。

### 7.4 ログメッセージの記載内容

- ログメッセージには、処理内容や発生した事象が分かる情報を記載する。
- 業務例外については、原因の特定につながる引数や対象情報を記録する。
- 正常処理の `INFO` ログについては、処理対象を特定できる識別情報を、可能な限り記録する。
- 処理対象を特定できる情報が取得できない場合は、無理に付与する必要はない。
- パスワードなどの機密情報は記録しない。

```java
// 商品コードに関する業務例外
log.info("商品コードが存在しません。商品コード: {}", itemCode);

// 正常な入庫登録
log.info("入庫登録が完了しました。入庫ID: {}", inboundId);

// 正常な在庫更新
log.info("在庫更新が完了しました。商品コード: {}", itemCode);
```

ログの出力先・ファイル保存・ローテーション・保存期間・出力形式・環境別ログレベルは、本規約ではなく技術設定で扱う。

## 8. SQLの記述規約

### 8.1 データベースオブジェクトの命名

- テーブル・ビュー・ストアドファンクション・ストアドプロシージャには、オブジェクト種別を示すプレフィックスを付ける。
- プレフィックス以降の名称は `lower_snake_case` とする。
- ストアドファンクション・ストアドプロシージャは、実装の有無にかかわらず命名規則のみ定義する。

| 対象 | プレフィックス | 命名例 |
| --- | --- | --- |
| マスターテーブル | `m_` | `m_item` |
| トランザクションテーブル | `t_` | `t_inventory_history` |
| ビュー | `v_` | `v_inventory_summary` |
| ストアドファンクション | `f_` | `f_calculate_stock` |
| ストアドプロシージャ | `p_` | `p_update_inventory` |

- カラム名はプレフィックスを付けず、`lower_snake_case` とする。
- DBで使用する用語・略語は `DB命名辞書.md` に従う。
- 名称は `name`、ステータス・状態は `status` とし、`nm`、`st` に短縮しない。
- 上記のオブジェクト名は命名例であり、実際のデータ構成を確定するものではない。

### 8.2 SQLの書式

- SQLキーワードは大文字、テーブル名・カラム名・別名などの識別子は小文字とする。
- `SELECT`、`FROM`、`WHERE`、`ORDER BY` などの句は独立した行に記述する。
- 各句の内容は次の行に記述し、半角スペース4文字でインデントする。
- 複数の項目を列挙する場合は、原則として1行に1項目ずつ記述する。
- `AND`・`OR` は条件式の先頭に記述する。
- 条件の追加・削除が想定される動的SQLなどでは `WHERE 1 = 1` を使用してよい。必須とはしない。

```sql
SELECT
    i.item_id,
    i.item_name
FROM
    m_item i
WHERE
    1 = 1
    AND i.item_id = :itemId
ORDER BY
    i.item_id;
```

### 8.3 JOINの書式

- `INNER JOIN`、`LEFT JOIN` などは独立した行に記述する。
- 結合先テーブル名は次の行に4スペースでインデントして記述する。
- `ON` は独立した行に記述する。
- 結合条件は `ON` と同じインデント位置に記述する。
- 結合条件が複数ある場合、`AND`・`OR` は条件式の先頭に記述する。

```sql
SELECT
    i.item_id,
    i.item_name,
    s.quantity,
    w.warehouse_name
FROM
    m_item i
INNER JOIN
    t_stock s
    ON i.item_id = s.item_id
INNER JOIN
    m_warehouse w
    ON s.warehouse_id = w.warehouse_id
WHERE
    1 = 1
    AND s.quantity > 0;
```

### 8.4 テーブル・ビューのエイリアス

- エイリアスは小文字とし、同一SQL文内で重複させない。
- 通常は `m_`、`t_`、`v_` などのプレフィックスを除いた名称の先頭1文字を使用する。
- 重複する場合は、重複する双方について先頭2文字、3文字と増やして区別する。
- 名称の先頭部分が共通する場合は、名称が分かれる部分のイニシャルを使用する。
- オブジェクト種別のみ異なり名称が同一の場合は、プレフィックスを利用して区別する。
- 同一テーブル・ビューを複数回参照する場合は、参照目的や抽出条件を表す名称のイニシャルと、対象名のイニシャルを組み合わせる。ビューの定義や自己結合でも同様とする。

| ケース | 対象 | エイリアス例 |
| --- | --- | --- |
| 通常 | `m_item` / `m_warehouse` / `t_stock` | `i` / `w` / `s` |
| 先頭文字が重複 | `m_item` / `t_inventory` | `it` / `in` |
| 名称が途中から分かれる | `t_item_history` / `t_item_detail` | `ih` / `id` |
| プレフィックスのみ異なる | `m_item` / `t_item` / `v_item` | `mi` / `ti` / `vi` |
| 同一テーブルを別目的で参照 | 通常在庫・保留在庫として `t_stock` を参照 | `ns` / `hs` |

### 8.5 SELECT文

- アプリケーションで使用するSQLでは、原則として取得するカラムを明示する。
- ビュー定義でも、原則として取得するカラムを明示する。
- データ確認・調査用の一時的なSQLでは、`SELECT *` を許可する。

### 8.6 INSERT文

- `INSERT INTO` と `VALUES` はそれぞれ独立した行に記述する。
- テーブル名、カラム名、値はインデントして記述する。
- カラム名と値は、原則として1行に1項目ずつ記述する。
- カラム名を省略せず明示する。

```sql
INSERT INTO
    m_item (
        item_code,
        item_name
    )
VALUES
    (
        :itemCode,
        :itemName
    );
```

### 8.7 UPDATE文

- `UPDATE`、`SET`、`WHERE` はそれぞれ独立した行に記述する。
- 更新対象のテーブル名はインデントして記述する。
- `SET` の各項目は1行ずつ記述し、最後の項目以外にカンマを付ける。
- `AND`・`OR` は条件式の先頭に記述する。

```sql
UPDATE
    m_item
SET
    item_name = :itemName,
    updated_at = CURRENT_TIMESTAMP
WHERE
    1 = 1
    AND item_id = :itemId;
```

### 8.8 DELETE文

- `DELETE FROM` と `WHERE` はそれぞれ独立した行に記述する。
- 削除対象のテーブル名はインデントして記述する。
- 原則として `WHERE` 句を必須とする。
- 全件削除が必要な場合は、目的と影響範囲を確認したうえで例外的に許可する。

```sql
DELETE FROM
    m_item
WHERE
    1 = 1
    AND item_id = :itemId;
```

### 8.9 NULLの取り扱い

- `NULL` の判定には `IS NULL` または `IS NOT NULL` を使用する。
- `NULL` を含む可能性がある条件式では、SQLの三値論理（TRUE・FALSE・UNKNOWN）を考慮する。
- `COALESCE()` などで `NULL` を別の値に置き換える場合は、業務上の意味を確認する。
- カラムの `NULL` 許容・非許容は、データ設計で決定する。

### 8.10 名前付きパラメータ

- Spring JDBCでは `NamedParameterJdbcTemplate` を使用する。
- SQLパラメータは `:itemId` のような名前付き形式とする。
- パラメータ名は `lowerCamelCase` とする。
- 利用者の入力値などをSQL文字列に直接連結しない。
- パラメータ化できないテーブル名・カラム名などの識別子は、別途安全に扱う。

### 8.11 SQLコメント

- 1行コメントには `-- ` を使用する。MySQLの仕様に従い、`--` の後に空白を入れる。
- 複数行コメントには `/* */` を使用する。
- SQLを読めば分かる内容には、不要なコメントを付けない。
- 処理内容そのものよりも、その条件や処理が必要な理由を記述する。
- 不要になったSQLをコメントアウトしたまま残さない。
