# DB命名辞書

## 1. 目的

本資料は、KAKUU WMSのデータベース設計・実装において使用する用語、英単語、略語を統一することを目的とする。

同じ意味を持つ用語に複数の表記が混在することを防ぎ、データベースの可読性・保守性を向上させる。

本資料はデータベースの命名を対象とする。Java側の命名については `コーディング規約.md` に従う。

## 2. 基本ルール

1. データベースのテーブル名・カラム名は、原則としてローワースネークケース（`lower_snake_case`）を使用する。
2. 本辞書に登録された用語は、採用する表記に統一する。
3. 辞書にない単語は、原則として省略せずに使用する。
4. 同じ意味の用語には、原則として同じ表記を使用する。
5. 新しい略語を使用する場合は、本辞書への追加を検討する。
6. Java側では、原則として英単語の短縮表記を使用しない。
7. 真偽値を表す場合は、意味が分かる名称を優先し、`fl` の使用は必要な場合に限る。

## 6. 状態・分類に関する命名

状態や分類を表す場合は、単純にフラグを使用するのではなく、値が持つ意味に応じて適切な用語を選択する。

| 日本語 | DBでの採用表記 | 用途 |
|---|---|---|
| ステータス・状態 | `st` | 現在の進行状況、業務状態、システム内部の状態 |
| 区分 | `type` | 種類・分類 |
| モード | `mode` | 動作モード |
| レベル | `level` | 段階・重要度 |
| フェーズ | `phase` | 工程段階 |
| カテゴリ | `category` | カテゴリ分類 |
| 種別 | `kind` | 一般的な種類・分類 |

DBでは、`status` と `state` を個別に使用せず、`st` に統一する。

Java側では略語を使用せず、`status` と `state` を用途に応じて使い分ける。

## 7. 真偽値・フラグに関する命名

### 7.1 基本方針

真偽値を表す名称では、何を判定する値なのかが分かる表記を優先する。

原則として、以下の接頭辞を使用する。

| 接頭辞 | 用途 | DBでの命名例 | Javaでの命名例 |
|---|---|---|---|
| `is` | 特定の状態であるか | `is_active` | `isActive` |
| `has` | 情報や状態を保持しているか | `has_stock` | `hasStock` |
| `can` | 処理を実行可能か | `can_ship` | `canShip` |
| `should` | 処理を実行すべきか | `should_retry` | `shouldRetry` |

### 7.2 `fl` の取り扱い

`fl` はDB命名辞書から削除せず、真偽値を表すための表記として使用可能とする。

ただし、原則として `is`、`has`、`can`、`should` などの意味が明確な名称を優先する。

また、複数の業務状態や分類を表す場合は、`fl` ではなく `st`、`type` などを使用する。

## 8. 運用ルール

1. DB設計時には本辞書を参照する。
2. 登録済みの用語は、原則として採用表記を使用する。
3. 辞書に存在しない用語は、意味が分かる英単語を使用する。
4. 新しい略語や表記の統一が必要になった場合は、辞書を更新する。
5. 本辞書の変更によって既存の設計資料や実装に影響がある場合は、影響範囲を確認する。
