# ブランチ運用ルール

## 1. 基本方針

KAKUU WMS では、`main` ブランチを常にレビュー済み・確定済みの状態として維持する。

`main` への直接コミットは原則禁止し、通常の作業は作業ブランチ上で行う。

作業ブランチは原則として `main` から作成する。

個人開発のため、複雑なブランチ階層は基本的に採用せず、変更履歴を追いやすいシンプルな運用を行う。

---

## 2. ブランチの種類

作業ブランチは、以下の3種類を基本とする。

| 種別 | 用途 |
|---|---|
| `feature` | 新規機能、設計、成果物の追加・作成 |
| `fix` | 誤り、不具合、不整合などの修正 |
| `docs` | プロジェクト管理資料、README、運用ルールなどのドキュメント作業 |

---

## 3. ブランチ命名規則

通常の作業ブランチには、対応するIssue番号を含める。

基本形式は以下とする。

```text
<type>/issue-<Issue番号>-<作業内容>
```

例：

```text
feature/issue-12-logical-er
fix/issue-18-screen-list
docs/issue-21-git-rules
```

作業内容部分は、ブランチの目的が判断できる簡潔な英語表記とする。

---

## 4. Issueとの対応

通常の作業では、Issueを作成してから対応する作業ブランチを作成する。

原則として、1つのIssueに対して1つの作業ブランチを対応させる。

```text
Issue
  ↓
mainから作業ブランチ作成
  ↓
作業・コミット
  ↓
Pull Request
  ↓
mainへマージ
```

Issue・Pull Requestの詳細な運用については、`Issue・PullRequest運用ルール.md` に従う。

---

## 5. サブブランチ

個人開発のため、サブブランチは原則として作成しない。

ただし、以下の場合は例外的にサブブランチを作成してよい。

- 1つのIssue内でも作業内容が大きく分かれる場合
- 一部の変更を切り離して検証したい場合
- 作業途中の変更を分離した方が、変更履歴を追いやすい場合
- その他、作業を分割した方が管理しやすいと判断した場合

サブブランチを使用する条件は厳密には定めず、作業の見通しや履歴の確認しやすさを優先して判断する。

サブブランチを使用する場合は、原則として親となる作業ブランチから作成する。

```text
main
  ↓
feature/issue-12-logical-er
  ↓
sub branch
```

サブブランチの変更は、最終的に親となる作業ブランチへ統合し、その後Pull Requestを通して `main` へマージする。

---

## 6. 作業中のmain更新

作業中に `main` が更新された場合は、必要に応じて最新の `main` の変更を作業ブランチへ取り込む。

KAKUU WMSでは変更履歴を保持する方針のため、履歴を書き換えるrebaseは原則使用せず、`main` を作業ブランチへmergeする方法を基本とする。

```text
main
  ↓
作業ブランチへmerge
```

不要な場合は、毎回 `main` の更新を取り込む必要はない。

---

## 7. コンフリクト

`main` の変更を取り込む際やブランチを統合する際にコンフリクトが発生した場合は、対象ファイルの内容と関連資料を確認して解消する。

単純に作業ブランチ側または `main` 側を優先するのではなく、最新の要求・要件・設計資料との整合性を確認した上で採用内容を判断する。

整合性の問題が別の成果物にも影響する場合は、`Issue・PullRequest運用ルール.md` に従い、必要に応じて別Issueとして管理する。

---

## 8. 長期間の作業ブランチ

作業ブランチを長期間維持することは原則として避ける。

作業範囲が大きくなりすぎた場合は、Issueや作業内容の分割を検討する。

ただし、個人開発であるため、ブランチの存続期間について明確な日数制限は設けない。

作業の目的や変更履歴が追跡できる状態を維持することを優先する。

---

## 9. Draft Pull Request

作業途中で変更内容をGitHub上から確認したい場合や、長めの作業で途中経過を残したい場合は、Draft Pull Requestを使用してよい。

Draft Pull Requestの使用は必須としない。

以下のような場合に使用を検討する。

- 作業途中の差分を確認したい場合
- Pull Request単位で途中経過を確認したい場合
- 作業期間が長くなる場合
- mainとの差分が大きくなる前に確認したい場合

mainへマージする場合は、Draft状態のままマージせず、`Ready for review` に変更した上で通常のPull Requestとして確認する。

---

## 10. 緊急修正

軽微かつ緊急性の高い修正については、例外的にIssueを作成せずに作業してよい。

例：

- 明らかな誤記
- リンク切れ
- 軽微な設定ミス
- 公開状態に影響する軽微な不備

ただし、緊急修正であっても `main` へ直接コミットは行わない。

修正用ブランチを作成し、Pull Requestを経由して `main` へ統合する。

```text
main
  ↓
修正用ブランチ
  ↓
コミット
  ↓
Pull Request
  ↓
main
```

Issueを作成しない場合は、コミットメッセージおよびPull Request本文から、変更理由と変更内容を確認できる状態にする。

緊急修正用ブランチではIssue番号を持たないため、以下のように作業内容が判断できるブランチ名を使用する。

```text
fix/typo-readme
fix/broken-link
docs/update-project-guide
```

緊急修正の範囲を超える変更が必要になった場合は、通常どおりIssueを作成して対応する。

---

## 11. マージ

作業完了後はPull Requestを作成し、`Create a merge commit` を使用して `main` へ統合する。

原則として以下のマージ方法は使用しない。

```text
Squash and merge
Rebase and merge
```

作業ブランチ上のコミット履歴を、mainへ統合した後も確認できる状態にすることを目的とする。

---

## 12. マージ後のブランチ

Pull Requestを `main` へマージした後は、作業ブランチを削除する。

マージ済みの作業ブランチは、後続作業で再利用しない。

追加修正が必要になった場合は、新しい作業ブランチを `main` から作成する。

通常作業の場合は、新しいIssueも作成する。

---

## 13. ブランチ運用の基本フロー

通常作業：

```text
Issue作成
    ↓
mainから作業ブランチ作成
    ↓
作業・コミット
    ↓
必要に応じてDraft Pull Request
    ↓
Pull Request
    ↓
Create a merge commit
    ↓
main
    ↓
作業ブランチ削除
```

緊急修正：

```text
mainから修正ブランチ作成
    ↓
修正・コミット
    ↓
Pull Request
    ↓
Create a merge commit
    ↓
main
    ↓
修正ブランチ削除
```
