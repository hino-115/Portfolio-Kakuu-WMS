# Issue・PullRequest運用ルール

## 1. 基本方針

KAKUU WMSでは、作業内容と変更理由を追跡できるようにするため、原則としてIssueを起点に作業を開始する。

Issueでは「何を行うか」を管理し、Pull Requestでは「どのように変更したか」と「mainへ統合してよい状態か」を確認する。

---

## 2. Issueの作成

作業開始前に、対応するIssueを作成する。

Issueは、1つの目的または1つの作業単位を基本とする。

### Issueに記載する内容

```text
## 概要

作業の目的や背景を記載する。

## 作業内容

- [ ] 実施する作業
- [ ] 実施する作業

## 完了条件

- [ ] 完了と判断する条件
- [ ] 必要な成果物が作成されている
- [ ] 関連資料との整合性が確認されている

## 後続作業

必要に応じて、このIssue完了後に実施する作業を記載する。
```

後続作業が存在しない場合は、省略してよい。

---

## 3. Issueの命名規則

Issueタイトルは日本語を基本とし、タイトルだけで作業対象と作業内容を判断できる名称とする。

原則として、以下の形式を使用する。

```text
<対象>を<作業内容>する
```

例：

```text
リポジトリ初期構成を作成する
論理エンティティを確定する
論理エンティティを正規化する
論理ER図を作成する
画面共通仕様を整理する
CHANGELOG運用方針を作成する
```

必要に応じて、以下の形式を使用してもよい。

```text
<対象>の<作業内容>
```

ただし、Issueは具体的な作業を表すため、可能な限り動詞で終わるタイトルを使用する。

以下のような、作業内容が判断しにくい名称は避ける。

```text
外部設計
設計修正
資料整理
ER図
対応
```

Issue番号はGitHubによって自動付与されるため、Issueタイトルには含めない。

---

## 4. Milestoneの命名規則

Milestoneは、プロジェクト管理・要求分析・要件定義・外部設計など、複数のIssueをまとめる工程または到達目標の管理に使用する。

Milestone名は、以下の形式を基本とする。

```text
M<連番>_<工程名>
```

例：

```text
M01_プロジェクト管理
M02_要求分析
M03_要件定義
M04_外部設計
M05_内部設計
M06_実装
M07_テスト
```

連番は工程または到達目標の実施順に付与する。

リポジトリ初期構成の作成、Git運用ルールの整備、ドキュメント管理ルールの整備などのプロジェクト管理作業についても、複数のIssueをまとめて管理する必要に応じてMilestoneを設定できる。

Milestoneを新しく追加する場合は、単一のIssueを管理するためではなく、複数のIssueをまとめて管理する必要があるかを確認した上で作成する。

---

## 5. Issueの粒度

Issueは、大きすぎず小さすぎない作業単位とする。

1つのIssue内に、目的の異なる複数の作業をまとめない。

### 適切な例

```text
論理エンティティを確定する
論理エンティティを正規化する
論理ER図を作成する
画面共通仕様を作成する
```

### 避ける例

```text
外部設計を全部作る
設計資料を修正する
いろいろ整理する
```

---

## 6. Issueとブランチの対応

Issueを作成した後、対応する作業ブランチを作成する。

原則として、1つのIssueに対して1つの作業ブランチを対応させる。

ブランチ名にはIssue番号を含める。

```text
<type>/issue-<Issue番号>-<作業内容>
```

例：

```text
feature/issue-12-logical-er
fix/issue-18-screen-list
docs/issue-21-git-rules
```

---

## 7. Issueのステータス管理

Issueは、作業開始時点ではOpenのままとする。

作業中は、Issue本文のチェックリストを更新し、進捗を確認できる状態にする。

Issueは、対応するPull Requestがmainへマージされ、完了条件を満たしたことを確認してからCloseする。

---

## 8. Pull Requestの作成

作業ブランチで必要な変更およびコミットが完了したら、`CHANGELOG運用方針.md` に従ってCHANGELOGへの記載要否を確認する。

記載対象となる変更がある場合は、CHANGELOGを更新し、独立したコミットとして記録した後、mainに対してPull Requestを作成する。記載が不要な場合は、CHANGELOGの更新・コミットを省略してよい。

Draft Pull Requestは原則使用しない。例外的に使用する場合は、Ready for reviewへの変更前に必要なCHANGELOGの更新・コミットを完了する。

CHANGELOGのコンフリクトが想定される場合もPull Requestを作成する。コンフリクトの解消はリポジトリの管理者が行う。

Pull Requestは、対応するIssueと紐づける。

Pull Requestの本文では、変更内容と確認結果が分かるようにする。

### Pull Requestに記載する内容

```text
## 概要

このPull Requestで行った変更の概要を記載する。

## 変更内容

- 変更した内容
- 追加した成果物
- 修正した内容

## 確認内容

- [ ] Issueの完了条件を満たしている
- [ ] 関連資料との整合性を確認した
- [ ] 不要なファイルが含まれていない
- [ ] ファイル名・配置がルールに従っている
- [ ] CHANGELOGの記載要否を確認し、必要な変更が反映されている

## 関連Issue

Closes #Issue番号
```

---

## 9. Pull RequestとIssueの紐づけ

Pull Requestには、対応するIssue番号を記載する。

原則として以下の形式を使用する。

```text
Closes #12
```

これにより、Pull Requestがmainへマージされた際に、対応するIssueを自動的にCloseできるようにする。

Issueを自動Closeしたくない場合は、単純に以下のように記載する。

```text
#12
```

---

## 10. 関連資料との整合性確認

設計や実装の変更により、既存資料との整合性が取れなくなる場合は、変更対象の成果物だけでなく、影響を受ける関連資料も確認する。

### 基本ルール

- 変更によって既存資料と内容が矛盾する場合は、そのままマージしない。
- 影響を受ける資料を特定し、同一Issue内で修正可能な範囲であれば合わせて修正する。
- 修正範囲が大きい場合や、別工程・別目的の作業になる場合は、新しいIssueを作成する。
- 関連資料の修正が必要だが、すぐに対応できない場合は、後続Issueとして明示する。
- Pull Requestでは、どの資料に影響があったかを変更内容または確認内容に記載する。

### 同一Issueで修正する例

論理ER図のエンティティ名を変更した結果、論理エンティティ一覧の名称も一致しなくなった場合。

```text
対象Issue:
論理ER図の修正

同時に修正:
- 論理ER図
- 論理エンティティ一覧
```

同一の設計対象に対する整合性修正であるため、同じIssue内で扱ってよい。

### 別Issueとする例

外部設計の変更により、内部設計や実装済みソースコードにも変更が必要になった場合。

```text
Issue A:
外部設計の画面仕様を変更

後続Issue B:
内部設計を外部設計の変更に合わせて修正

後続Issue C:
実装を変更後の設計に合わせて修正
```

工程や目的が異なる場合は、無理に1つのIssueへまとめず、関連Issueとして追跡する。

### 上流工程へ戻る場合

後工程の作業中に、要求分析・要件定義・外部設計などの上流工程に誤りや不足が見つかった場合は、上流資料を修正するためのIssueを作成する。

修正後は、下流成果物への影響を確認し、必要に応じて追加Issueを作成する。

```text
実装中に要件の不整合を発見
    ↓
要件定義修正Issueを作成
    ↓
要件定義を修正
    ↓
外部設計・内部設計への影響確認
    ↓
必要な修正Issueを作成
    ↓
実装を修正
```

上流資料を修正せず、下流成果物だけを合わせる運用は原則行わない。

---

## 11. Pull Requestの確認

個人開発であっても、mainへ直接統合せず、Pull Requestを確認してからマージする。

最低限、以下を確認する。

- Issueの目的を満たしている
- 必要な成果物が揃っている
- 関連する要求・要件・設計との不整合がない
- 変更によって他の成果物との整合性が崩れていない
- 必要な関連資料の修正または後続Issueの作成が行われている
- ファイル配置が正しい
- 命名規則に従っている
- 不要な一時ファイルや作業ファイルが含まれていない
- コミット履歴から作業過程を確認できる
- CHANGELOGの記載要否および記載内容が実際の変更内容と一致している

---

## 12. Pull Requestのマージ

リポジトリの管理者がPull Requestを確認し、CHANGELOGにコンフリクトがある場合は解消した上で、`Create a merge commit` を使用してmainへ統合する。

原則として以下は使用しない。

```text
Squash and merge
Rebase and merge
```

作業ブランチのコミット履歴をmain側でも確認できる状態を維持するためである。

---

## 13. マージ後の処理

Pull Requestをmainへマージした後、以下を実施する。

1. 対応するIssueがCloseされていることを確認する。
2. 作業ブランチを削除する。
3. 後続Issueがある場合は、その内容と関連性を確認する。

同じブランチを後続作業に再利用しない。

---

## 14. 追加修正が発生した場合

マージ済みの成果物に追加修正が必要になった場合は、既存のIssueや削除済みブランチを再利用しない。

原則として以下の流れで対応する。

```text
新しいIssueを作成
  ↓
mainから新しいブランチを作成
  ↓
修正
  ↓
Pull Request
  ↓
Create a merge commit
```

これにより、修正理由と変更履歴を作業単位で追跡できる状態を維持する。
