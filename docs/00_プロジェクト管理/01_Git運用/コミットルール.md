# コミットルール

## 1. 基本方針

KAKUU WMS では、コミット履歴から変更内容と作業過程を追跡できるようにする。

コミットメッセージは、Conventional Commits を参考にしつつ、以下の形式を基本とする。

```text
<type>(<scope>): <日本語本文>
```

例：

```text
feat(external-design): 論理ER図を追加
fix(requirements): 画面一覧の表記を修正
docs(project): ブランチ運用ルールを追加
```

コミット本文は日本語を基本とする。

---

## 2. type

`type` は変更の種類を表す。

| type | 用途 |
|---|---|
| `feat` | 新規機能、新規設計、新規成果物の追加 |
| `fix` | 誤記、不整合、不具合などの修正 |
| `docs` | README、運用ルール、説明資料などのドキュメント変更 |
| `refactor` | 機能や意味を変えずに構成や実装を整理 |
| `test` | テストの追加・修正 |
| `chore` | 設定変更、環境整備、その他の保守作業 |

### 使用例

```text
feat(requirements): 機能要件一覧を追加
fix(requirements-analysis): 概念ER図の多重度を修正
docs(project): コミットルールを追加
refactor(external-design): データ設計資料の構成を整理
test(test): 入荷登録機能のテストケースを追加
chore(project): GitHub設定を変更
```

---

## 3. scope

`scope` は変更対象となる工程または領域を表す。

現時点では以下を使用する。

| scope | 対象 |
|---|---|
| `project` | プロジェクト管理、Git運用、README、設定など |
| `requirements-analysis` | 要求分析 |
| `requirements` | 要件定義 |
| `external-design` | 外部設計 |
| `internal-design` | 内部設計 |
| `implementation` | 実装 |
| `test` | テスト |

例：

```text
feat(requirements-analysis): 概念ER図を追加
feat(requirements): 上位DFDを追加
feat(external-design): 論理エンティティ一覧を追加
feat(internal-design): テーブル定義を追加
feat(implementation): 商品検索処理を追加
test(test): 商品検索のテストケースを追加
```

実装フェーズでは、`src` の構成やアプリケーションのレイヤ構成が確定した時点で、`implementation` のscopeを細分化する必要があるか再検討する。

---

## 4. 日本語本文

日本語本文では、変更対象と変更内容が分かるように記述する。

### 推奨

```text
feat(external-design): 論理ER図を追加
fix(requirements): 画面一覧の誤記を修正
docs(project): CHANGELOG運用方針を追加
```

### 避ける例

```text
fix: 修正
feat: 追加
chore: 更新
```

コミット一覧だけを見ても、何を変更したのか判断できる内容とする。

---

## 5. コミット単位

1コミットにつき1つの目的を原則とする。

複数の独立した変更を1コミットにまとめない。

例として、以下の作業を同時に行った場合は可能な限り分割する。

```text
feat(external-design): 論理エンティティ一覧を追加

docs(project): 外部設計のREADMEを更新
```

一方、1つの成果物を完成させるために密接に関連する変更は、同一コミットとして扱ってよい。

---

## 6. 作業途中のコミット

KAKUU WMS では、作業過程をGit履歴から確認できることを重視する。

そのため、完成時だけでなく、意味のある作業単位でコミットを行う。

例：

```text
feat(external-design): 論理エンティティ初版を作成
feat(external-design): 論理エンティティに属性を追加
fix(external-design): エンティティ間の関係を修正
feat(external-design): 論理ER図を追加
```

ただし、以下のような変更内容が判断できないコミットメッセージは原則使用しない。

```text
WIP
途中
修正
更新
test
```

---

## 7. Issueとの関係

作業は原則としてIssueを起点とする。

Issue番号はブランチ名に含めるため、コミットメッセージへのIssue番号の記載は必須としない。

例：

```text
ブランチ:
feature/issue-12-logical-er

コミット:
feat(external-design): 論理ER図を追加
```

Issue、作業ブランチ、Pull Requestを通して変更の目的を追跡する。

---

## 8. 過去版の管理

過去版を保存するためだけの `old` フォルダは原則作成しない。

成果物の変更履歴はGitのコミット履歴から確認する。

そのため、既存成果物を大きく変更する場合も、変更前の状態をコミットとして残してから作業を進める。

---

## 9. マージとの関係

作業ブランチでは、作業過程が分かるよう複数のコミットを残してよい。

Pull Requestのマージには原則として `Create a merge commit` を使用する。

`Squash and merge` によって作業ブランチ上のコミットを1つにまとめる運用は原則行わない。

これにより、mainへ統合した後も作業過程を確認できる状態を維持する。
