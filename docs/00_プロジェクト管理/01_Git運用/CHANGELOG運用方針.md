# CHANGELOG運用方針

## 1. 目的

KAKUU WMSでは、プロジェクトにおける主要な変更内容を外部から確認しやすくするため、リポジトリルートに `CHANGELOG.md` を配置する。

Gitのコミット履歴では作業過程や細かな変更を管理し、CHANGELOGではプロジェクト全体に影響する主要な変更を要約して記録する。

---

## 2. 配置場所

CHANGELOG本体は、リポジトリルートに配置する。

```text
kakuu-wms/
└─ CHANGELOG.md
```

CHANGELOGの記載・更新ルールは以下に配置する。

```text
docs/
└─ 00_プロジェクト管理/
   └─ 01_Git運用/
      └─ CHANGELOG運用方針.md
```

---

## 3. Git履歴との役割分担

Gitのコミット履歴とCHANGELOGは、以下のように役割を分ける。

### Git履歴

以下を確認するために使用する。

- 作業過程
- 個別ファイルの変更
- 細かな修正
- 変更順序
- 作業ブランチ内のコミット履歴

### CHANGELOG

以下を確認するために使用する。

- 主要な成果物の追加
- 仕様や設計の重要な変更
- 大きな構成変更
- 不具合や不整合の主要な修正
- 成果物や機能の削除

すべてのコミットをCHANGELOGへ転記する運用は行わない。

---

## 4. 基本構成

未リリースの変更は `Unreleased` に記載する。

```text
## Unreleased

### Added

### Changed

### Fixed

### Removed
```

分類は以下を基本とする。

| 分類 | 内容 |
|---|---|
| `Added` | 新しい機能、設計資料、成果物などの追加 |
| `Changed` | 既存仕様、設計、構成などの変更 |
| `Fixed` | 不具合、誤記、不整合などの修正 |
| `Removed` | 機能、設計、成果物などの削除 |

必要性が生じた場合は、分類の追加を検討する。

---

## 5. 記載対象

CHANGELOGには、外部から確認した際にプロジェクトの変化として意味を持つ変更を記載する。

### 記載する例

- 要求分析書を追加
- 概念ER図を追加
- 要件定義書を追加
- 論理ER図を追加
- 主要なフォルダ構成を変更
- 画面仕様を大きく変更
- 既存設計との重要な不整合を修正
- 不要となった成果物を削除

### 原則として記載しない例

- 軽微な誤字修正
- Markdownの空白調整
- 表示上の軽微な整形
- コメントのみの修正
- 作業途中の細かな変更

ただし、変更の重要度に応じて記載してよい。

---

## 6. 更新タイミング

CHANGELOGは、作業ブランチ上でCHANGELOGの更新を除くすべての作業およびコミットが完了した後、Pull Requestを作成する前に更新する。

記載対象となる変更がある場合は、同じ作業ブランチ上で `CHANGELOG.md` を更新し、CHANGELOGの更新を独立したコミットとして記録する。その後、Pull Requestを作成する。

CHANGELOGへ記載する必要がない変更については、更新を必須としない。

### 更新手順

```text
作業・コミット完了
    ↓
CHANGELOGへの記載要否を確認
    ↓
必要に応じてCHANGELOG.mdを更新・コミット
    ↓
Pull Request作成
```

---

## 7. Pull Requestとの関係

Pull Requestには、記載対象となる変更がある場合、CHANGELOGの更新コミットを含める。

Pull Request確認時には、CHANGELOGの記載要否および記載内容が実際の変更内容と一致しているかを確認する。

CHANGELOGの更新だけを目的とした修正が必要になった場合は、通常のIssue・ブランチ運用に従う。

軽微かつ緊急性の高い修正については、ブランチ運用ルールに定める緊急修正の扱いに従う。

### CHANGELOGのコンフリクト

CHANGELOGのマージ時にコンフリクトが発生した場合は、リポジトリの管理者が変更内容を確認し、必要な記載内容を保持した上でコンフリクトを解消してマージを行う。

---

## 8. バージョン管理

現時点では、開発途中の変更は `Unreleased` を中心に管理する。

正式なバージョン番号を使用する時期と命名方法については、実装・リリース方針が明確になった時点で決定する。

バージョン番号を導入するまでは、無理にバージョンを付与しない。

---

## 9. 運用方針の見直し

プロジェクトの進行に伴い、CHANGELOGの粒度や分類が適さなくなった場合は、本方針を見直してよい。

変更する場合は、通常のIssue・Pull Request運用に従って更新する。
