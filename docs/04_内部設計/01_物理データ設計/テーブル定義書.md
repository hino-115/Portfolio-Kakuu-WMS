# テーブル定義書

## 1. 目的

本資料は、KAKUU WMSの論理データ設計の結果を基に、データベースの物理的な構造を定義することを目的とする。

論理エンティティ、属性、キーおよび関連の定義を基に、物理テーブル名、物理カラム名、データ型、桁数、制約等を定義する。

本資料は内部設計の成果物とし、データベースの構築、SQLの作成およびアプリケーションの実装における基準とする。

## 2. 共通設計方針

### 2.1 データベース基本設定

| 項目 | 設定値 |
| --- | --- |
| DBMS | MySQL 8.4 LTS |
| データベース名 | kakuu_wms |
| ストレージエンジン | InnoDB |

文字コードおよび照合順序は、原則としてデータベースの基本設定を使用する。個別に異なる設定が必要な場合は、対象のテーブル定義に記載する。

関連資料：[技術選定.md](../../00_プロジェクト管理/03_技術方針/技術選定.md)

### 2.2 命名規則

テーブル名およびカラム名は、コーディング規約およびDB命名辞書に従う。

| 対象 | 命名形式 |
| --- | --- |
| データベース名 | lower_snake_case |
| マスターテーブル | m_ + lower_snake_case |
| トランザクションテーブル | t_ + lower_snake_case |
| システム管理用テーブル | s_ + lower_snake_case |
| カラム名 | lower_snake_case |
| 主キー | PRIMARY |
| 外部キー | fk_テーブル名_対象カラム名 |
| 一意制約 | uq_テーブル名_対象カラム名 |
| CHECK制約 | ck_テーブル名_制約内容 |
| インデックス | idx_テーブル名_対象カラム名 |

- 制約名およびインデックス名に使用するテーブル名は、接頭辞を含める。
- 複数のカラムを対象とする場合は、対象カラム名を設定順に連結する。
- 識別子は64文字以内とする。
- 名称を短縮する場合は、意味が分かる名称とする。

関連資料：

- [コーディング規約.md](../../00_プロジェクト管理/03_技術方針/コーディング規約.md)
- [DB命名辞書.md](../../00_プロジェクト管理/03_技術方針/DB命名辞書.md)

### 2.3 データ型

| 対象 | データ型 | 理由 |
| --- | --- | --- |
| システム内部ID | INT / BIGINT | 累積採番数に応じて設定する |
| 業務コード | CHAR(n) / VARCHAR(n) | 英数字や先頭の0を保持する |
| 業務番号 | CHAR(n) / VARCHAR(n) / INT | 採番形式や外部データに対応する |
| 名称 | VARCHAR(n) | 可変長の文字列を保持する |

- マスターテーブルの内部IDは原則としてINTとする。
- トランザクションテーブルの内部IDは累積採番数に応じてINTまたはBIGINTとする。
- 外部キーおよびID保持属性は、参照先のIDと同じ型とする。

### 2.4 採番方式

| 対象 | 採番方式 |
| --- | --- |
| システム内部ID | AUTO_INCREMENT |
| 業務コード | 接頭辞＋手動入力・接頭辞＋自動連番の併用、または接頭辞＋自動連番のみ |
| 業務番号 | 各テーブル定義で決定 |

システム内部IDは変更・再利用を禁止し、欠番を許容する。

#### コード系の共通採番ルール

| 項目 | 内容 |
| --- | --- |
| 接頭辞 | 半角英大文字3文字 |
| 区切り文字 | なし |
| 接頭辞の付与 | システム側で自動付与 |
| 自動連番開始値 | 10000 |
| 自動連番桁数 | 6桁・ゼロ埋め |
| 予備領域 | 1～9999 |
| 手動採番 | 接頭辞以降を利用者が入力 |
| 自動採番のみの場合 | 登録後のコード変更不可 |

手動・自動併用方式では登録後のコード変更を許容する。自動採番開始値は内部IDのAUTO_INCREMENTには適用しない。

変更可能なコード・番号は、論理削除されていないデータ（無効データを含む）内で一意であれば設定・再利用可能とする。自動採番のみのコード・番号は変更・再利用を禁止する。日単位・ヘッダー単位のリセットは個別採番方式に従う。

#### 連番管理

| 項目 | 内容 |
| --- | --- |
| 初回採番 | 開始採番値から発行する。 |
| 通常採番 | 最終採番値を更新する。 |
| 重複時処理 | 手動入力済みのコード・番号と重複した場合は新規採番する。 |
| 日付切替 | 基準日がNULL以外かつ当日と異なる場合、基準日を当日に更新し、開始採番値から採番する。NULLの場合はリセットしない。 |
| 上限到達 | 最大採番値を超える採番要求はエラーとする。 |
| 排他制御 | 保留。後続設計で検討する。 |
| ロールバック | 採番値は使い捨てとし、巻き戻さない。採番処理は業務処理とは独立したトランザクションで確定する。 |

採番値の欠番を許容する。採番管理テーブルは5.1を参照する。

### 2.5 共通カラム

| 論理名 | 物理名 | データ型 | NOT NULL | デフォルト値 |
| --- | --- | --- | :---: | --- |
| データ状態 | data_status | TINYINT | ○ | 0 |
| 登録日時 | created_dtm | DATETIME | ○ | — |
| 登録者 | created_by | INT | ○ | — |
| 更新日時 | updated_dtm | DATETIME | ○ | — |
| 更新者 | updated_by | INT | ○ | — |

登録者および更新者のデータ型は、社員IDと一致させる。共通カラムの有無は論理エンティティ属性定義に従う。CSV取込結果は登録日時・登録者のみを保持する。採番管理テーブルは共通カラムを保持しない。新規登録時は更新日時・更新者に登録日時・登録者と同じ値を設定し、更新・論理削除時は更新日時・更新者を更新する。登録日時・登録者は維持する。データ状態の各値の意味は別途定義する。

### 2.6 制約

| 制約 | 設定方針 |
| --- | --- |
| PRIMARY KEY | 論理キー設計に従って設定する |
| FOREIGN KEY | 論理キー設計でFKと定義された属性に設定する |
| UNIQUE | 条件を伴わない一意性に対して設定する |
| NOT NULL | 論理属性定義の必須・任意に従って設定する |
| CHECK | 値の範囲や状態など、必要に応じて設定する |

- 外部キーによる連鎖削除・連鎖更新は行わない。
- 条件付き一意性はDB制約として設定せず、アプリケーション側で制御する。
- DB制約で実現しない条件は、アプリケーション側で制御する。

### 2.7 インデックス

- 各テーブル定義にインデックスの記載欄を設ける。
- 現段階では、検索・性能向上を目的としたインデックスの設定は行わない。
- 後続の設計・実装でSQLの検索条件や結合条件に応じて設定する。
- 性能確認の結果に応じて追加・変更・削除を行う。

PK・FK・UNIQUE制約に伴うインデックスは、制約の設定に従う。

### 2.8 定義の表記

仮定義、案の提示、確定の順に検討する。未決定事項は「要確認」、提案値は「25（案）」等と記載し、確定後に案の表記を外す。

| 表記 | 意味 |
| --- | --- |
| ○ | NOT NULL |
| × | NULL許容 |
| — | 設定なし・該当なし |
| 要確認 | 未決定 |
| （案） | 確認待ちの提案 |
